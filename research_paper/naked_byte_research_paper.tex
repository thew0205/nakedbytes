\section{Methodology}

This paper resents a comparative experimental evaluation of three serialization frameworks— NakedBytes, FlatBuffers, and Protocol Buffers—with the objective of providing a holistic and practically relevant analysis of their behavior across constrained and general-purpose systems. The evaluation is designed to capture not only serialized size, but also runtime, memory usage, and compatibility characteristics that are critical in energy-sector and embedded deployments.

\subsection{Evaluation Parameters}

The analysis focuses on the following primary parameters:

\begin{itemize}
    \item \textbf{Resulting Binary Size}: The size of the serialized output buffer produced by each framework for equivalent data structures. This metric captures the efficiency of the on-wire or stored representation, including all internal metadata.

    \item \textbf{Code Size and Static Memory Usage}: This includes the compiled program size (flash/ROM footprint) and static RAM usage introduced by the serialization framework and generated code.

    \item \textbf{Computation Time}: The execution time required for serialization and deserialization operations, measured separately. This includes the cost of parsing, offset resolution, and field access in the native programming language.

    \item \textbf{Memory Usage}: The runtime memory requirements during serialization and deserialization, including:
          \begin{itemize}
              \item Stack usage
              \item Heap usage (if any)
              \item Temporary buffers or scratch memory
          \end{itemize}

    \item \textbf{Compatibility Properties}: The support for forward and backward compatibility, including schema evolution behavior, optional fields, and handling of missing or unknown fields.
\end{itemize}

These parameters were selected based on prior empirical studies of serialization frameworks and reflect constraints commonly encountered in embedded energy systems, industrial devices, and microcontroller-based platforms.

\subsection{Experimental Design}

The experiments were carefully curated to isolate individual costs and minimize measurement noise. All benchmarks were conducted using equivalent logical data models and access patterns across frameworks. Where applicable, generated code was used rather than hand-written adapters, reflecting real-world usage.

To enable fine-grained analysis, the experiments were divided into the following categories:

\begin{itemize}
    \item \textbf{Baseline Overhead}: A minimal program containing only framework utilities and generated code, used to determine default code size and static memory overhead.

    \item \textbf{Deserialization Only}:
          \begin{itemize}
              \item Deserialization without field access
              \item Deserialization with single-field access
              \item Deserialization with full-field access
              \item Deserialization with nested-field access
          \end{itemize}

    \item \textbf{Serialization Only}:
          \begin{itemize}
              \item Serialization without field access
              \item Serialization with single-field access
              \item Serialization with full-field access
              \item Serialization with nested-field access
          \end{itemize}

    \item \textbf{Combined Serialization and Deserialization}:
          \begin{itemize}
              \item Serialization followed by deserialization without field access
              \item Serialization and deserialization with single-field access
              \item Serialization and deserialization with full-field access
              \item Serialization and deserialization with nested-field access
          \end{itemize}
\end{itemize}

This decomposition allows the separation of pure encoding/decoding costs from access-related overhead and highlights the impact of nested structures and variable-length fields.

\subsection{Deserialization Performance}

Tables~1–3 summarize deserialization performance under release builds for three access patterns: no field access, single-field access, and full-field access.

In the \textit{deserialization without field access} case, NakedBytes and FlatBuffers exhibit near-zero net execution time, reflecting their ability to treat serialized data as an in-place memory view. In contrast, Protocol Buffers and NanoPB incur significantly higher costs due to full message parsing and object reconstruction. Protocol Buffers shows average deserialization times exceeding 18\,ms, while NanoPB exceeds 54\,ms, even without accessing any fields.

When a \textit{single primitive field} is accessed, NakedBytes and FlatBuffers incur only marginal additional cost, as shown in Table~2. NakedBytes consistently achieves the lowest latency, followed closely by FlatBuffers. Protocol Buffers and NanoPB demonstrate a substantial increase in execution time, indicating that field access triggers additional decoding and data copying operations.

For \textit{full-field access} (Table~3), the performance gap widens further. NakedBytes maintains sub-millisecond execution times, while FlatBuffers exhibits a moderate increase due to offset resolution and accessor logic. Protocol Buffers and NanoPB remain one to two orders of magnitude slower, reflecting the cumulative cost of decoding all fields into runtime representations.

Overall, these results demonstrate that zero-copy and offset-based designs scale more favorably with access complexity compared to parse-and-materialize approaches.

\subsection{Serialization Performance}

Serialization results for release builds are presented in Tables~4 and~5. NakedBytes consistently achieves the lowest serialization time, particularly when serializing primitive fields or the full data structure. This behavior is attributed to its direct in-place buffer construction, which avoids intermediate representations and dynamic memory allocation.

FlatBuffers shows significantly higher serialization costs, especially for full-structure serialization. This overhead arises from backward buffer construction, object graph traversal, and builder management. Although FlatBuffers provides efficient deserialization, its serialization path is comparatively expensive.

Protocol Buffers exhibits moderate serialization times but incurs substantial code size and static memory overhead, as discussed in Section~\ref{sec:memory}. NanoPB shows the highest serialization latency among embedded-focused frameworks, primarily due to field-by-field encoding and explicit bounds checking.

\subsection{Impact of Debug Builds}

Tables~6–10 present corresponding results under debug (\texttt{-O0}) builds. Across all frameworks, execution time increases significantly due to the absence of compiler optimizations. However, the relative performance ordering remains consistent.

NakedBytes continues to outperform other frameworks even in debug builds, demonstrating that its performance advantages are largely structural rather than compiler-dependent. FlatBuffers experiences a pronounced slowdown, particularly during full-field deserialization, indicating sensitivity to optimization levels. Protocol Buffers and NanoPB suffer the largest absolute slowdowns, further emphasizing the cost of parsing-heavy designs in unoptimized builds.

These results are particularly relevant for embedded development workflows, where debug builds are frequently used during testing and validation.

\subsection{Binary Size and Memory Footprint}

Across all experiments, NakedBytes and FlatBuffers maintain small and predictable serialized buffer sizes. NakedBytes produces slightly larger buffers than Protocol Buffers in some cases due to explicit offset storage, but this overhead remains constant and independent of access patterns.

Protocol Buffers achieves compact wire representations; however, this advantage is offset by its substantial flash and static RAM usage. On embedded targets, Protocol Buffers consistently requires over 2.7\,MB of flash and more than 150\,KB of static RAM, rendering it impractical for microcontroller-class devices. NanoPB significantly reduces this footprint but still incurs higher runtime costs compared to NakedBytes and FlatBuffers.

Notably, NakedBytes introduces negligible static RAM usage across all experiments, reinforcing its suitability for memory-constrained environments.

\subsection{Discussion Summary}

The experimental results highlight clear trade-offs among the evaluated serialization frameworks:

\begin{itemize}
    \item NakedBytes consistently achieves the lowest serialization and deserialization latency, minimal static memory usage, and predictable binary layouts.
    \item FlatBuffers provides efficient zero-copy deserialization but incurs higher serialization costs and moderate code-size overhead.
    \item Protocol Buffers prioritizes portability and schema evolution at the expense of execution time and memory footprint.
    \item NanoPB reduces Protocol Buffers’ memory footprint but remains significantly slower than offset-based approaches.
\end{itemize}

These findings suggest that offset-oriented, in-place serialization frameworks are better suited for embedded and energy-sector applications where deterministic performance, low latency, and minimal memory usage are critical.
